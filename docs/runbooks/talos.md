# Configure Talos disk encryption with azath
This runbook covers configuring Talos Linux nodes to use azath as a KMS for disk encryption key sealing and unsealing.

Use a Talos [KMS key slot](https://www.talos.dev/v1.10/talos-guides/configuration/disk-encryption/#kms-key-slot) for the encrypted partitions. See [Architecture and threat model](../architecture/mvp.md) for the server trust model.

## Prerequisites
- At least one deployed, healthy azath server. If using redundant servers, keep their device lists and master keys consistent.
- A device (node) entry for each Talos node in the azath server config.
- A Talos version with KMS key-slot support. The example uses the [Talos v1.10 disk-encryption configuration](https://www.talos.dev/v1.10/talos-guides/configuration/disk-encryption/#kms-key-slot); check the schema for your Talos version. Live Talos compatibility is not established by this repository's tests.

## Step 1: Register Talos nodes
Identify the UUID that the Talos KMS client sends as `node_uuid`; do not use an arbitrary UUID generated by `config new-device`. Verify the identity on your target Talos version before relying on boot-time unlocking. Add a device entry for each node to every azath server config:

```yaml
devices:
  - name: talos-worker-01
    uuid: 660e8400-e29b-41d4-a716-446655440001
    disabled: false
  - name: talos-control-01
    uuid: 770e8400-e29b-41d4-a716-446655440002
    disabled: false
```

Deploy the updated config and restart every azath server before provisioning encryption.

## Step 2: Configure Talos KMS
Configure Talos machine config to use the azath KMS endpoint for disk encryption (supported on `state` and `ephemeral` partitions):

```yaml
machine:
  systemDiskEncryption:
    state:
      provider: luks2
      keys:
        - slot: 0
          kms:
            endpoint: https://azath-lan.example.internal:443
    ephemeral:
      provider: luks2
      keys:
        - slot: 0
          kms:
            endpoint: https://azath-lan.example.internal:443
```

### Failover
**Unverified**: native Talos KMS failover between multiple endpoints is not tested in the current MVP. The example config has one KMS endpoint per key slot. If that endpoint is unavailable at boot, the node will not unseal its disk.

Options for failover:

1. **Single DNS name with multiple A records**: validate Talos address selection and retries before relying on a name that resolves to both LAN and VPS IPs.
2. **Single VPS endpoint**: use the VPS address if nodes must connect independently of the LAN server. LAN-side sealing and unsealing then depend on internet access.
3. **Separate config per location**: use different machine configs for nodes behind the LAN and nodes behind the VPS.

The MVP explicitly does not claim native failover. If you test and validate a specific failover strategy, update this document.

## Step 3: Apply the config
Back up node data and keep a recovery method available before changing disk-encryption settings. Confirm the target node in your `talosctl` context, then apply the version-appropriate patch:

```bash
talosctl apply-config -f patched-config.yaml
talosctl reboot
```

At boot, Talos calls azath `Unseal` to get the disk encryption key. The first unseal requires Telegram approval; subsequent unseals within the approval cache TTL are approved automatically.

## Recover after an approval failure
If Telegram is unavailable and no valid approval-cache entry exists, Talos receives random bytes rather than the disk key. Restore Telegram access before retrying the boot and approve the request.

For node authorization and sealed-blob storage, see [Client integration](../reference/clients.md#talos).

## Re-provisioning after master key rotation
If the azath master key changes, Talos nodes cannot unseal their disks because the old sealed blobs are tied to the old key. Steps to recover:

1. Keep the old master key available and back up data while nodes can still unlock with it. azath does not migrate or rewrap existing blobs.
2. Plan and validate a Talos-version-specific re-provisioning procedure before replacing any server key. Re-provisioning can destroy data.
3. Deploy the new master key and restart every azath server when the recovery plan permits it. Newly sealed keys use the new master key; old blobs still require the old key.
